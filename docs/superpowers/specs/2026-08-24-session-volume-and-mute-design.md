# 活跃应用会话音量与静音设计

日期：2026-08-24
状态：设计方向已确认，等待本文档审阅后进入实施

## 一句话目标

在不增加驱动、第三方依赖、新轮询或新权限的前提下，让活跃应用的当前音量不再被刷新重置，并补上可恢复原音量的逐应用静音，同时统一“自动接管”和“手动启用”的真实状态。

## 成功标准

- Process Tap 应用首次出现时仍以已保存值或用户配置的默认输出增益作为初始值；全新安装的默认值为 75%。
- 用户把某个活跃应用调到 42% 后，面板经历多次 1 秒刷新仍保持 42%，不会回到 75% 或历史保存值。
- 点击逐应用静音后音量变为 0%；再次点击恢复本次静音前的精确值。没有可恢复值时，Process Tap 应用优先采用非零的已记住值或用户默认值，AppleScript 应用采用 75% 基准；所有候选都是 0 时也用 75%，保证“恢复”不会成为无效操作。
- Process Tap 静音是会话状态，不把 0% 写入“记住每个应用的增益”，应用下次出现时不会因为本次静音而继续静音。
- 开启“自动接管新应用”后，滑杆、状态文字和操作按钮都与实际接管状态一致。
- 未手动启用且未选择自动接管的 Process Tap 应用不会因新增静音按钮而触发系统音频捕获。
- 不引入新依赖、虚拟驱动、EQ、持续 DSP、额外定时器或额外权限；保留面板可见时现有的 1 秒发现刷新。

## 可证实事实与市场参照

- [SoundSource 的应用控制文档](https://www.rogueamoeba.com/support/manuals/soundsource/?page=application-adjustments)明确提供逐应用音量、静音、定时静音、路由和收藏。本文只选取静音这个高频、低复杂度能力。
- [Background Music v0.5.0](https://github.com/kyleneideck/BackgroundMusic/releases/tag/v0.5.0)加入逐应用静音，并在没有音频播放时停止处理；它依赖虚拟音频驱动，不适合直接复制到本项目。
- [MacMixer](https://github.com/burghr/MacMixer)采用原生 Core Audio Process Tap，提供逐应用滑杆、输出选择和主音量；路线与本项目接近，但本项目继续保持更小的功能面。
- [Waves](https://github.com/JonathanRReed/Waves)同样采用 Process Tap，并提供逐应用音量、静音、增强、EQ、配置与路由。其较大功能面和依赖不属于本轮轻量目标。
- [Apple 的 Core Audio Tap 文档](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps)说明 Process Tap 用于捕获指定进程或进程组输出，并可配合聚合设备工作；首次使用相关捕获路径可能触发系统音频录制权限。

没有权威来源给出这些产品可横向比较的 CPU、内存或延迟数据，因此本文不宣称本项目比它们“更快”。“更轻量”只由可核验的工程约束表达：无第三方依赖、无虚拟驱动、无常驻 DSP，并记录构建产物与运行资源的前后变化。

## 当前问题

### 1. 会话音量存在两个真相

Process Tap 应用每次发现时，都从 `VolumeSettingsStore` 重新生成 `reportedVolume`。随后刷新流程又用这个值覆盖 `applicationVolumes`。面板可见时每秒发现一次，因此在关闭“记住每个应用的增益”时，用户刚刚设置的会话值会被默认 75% 覆盖；开启记忆时，也可能被上次保存值覆盖。

设置值只应负责应用本次出现时的初始化，不能持续覆盖当前会话。

### 2. 接管状态存在多个判断口径

Process Tap 管理器允许“手动启用”或“自动接管新应用”任一条件成立时创建 Tap，但滑杆、状态文字和行内按钮只检查手动启用集合。于是自动接管可能已经生效，界面却仍显示“未启用”且不允许调节。

### 3. 缺少轻量的逐应用静音入口

当前只能把滑杆拖到 0%，没有一键静音，也没有恢复静音前音量的会话记录。这是市场同类工具普遍具备、同时不需要新音频架构的能力。

## 范围

本轮包括：

- 修复 Process Tap 会话值被刷新重置。
- 抽出统一的有效接管谓词，并让管理器、滑杆、状态和按钮复用。
- 增加逐应用静音/恢复按钮与会话级恢复值。
- 增加纯逻辑回归测试、双语 README 功能说明和发布前验证记录。
- 在 README 和界面帮助中明确：Process Tap 静音控制的是归并后应用进程的系统级输出，不读取或改变内部播放器音量，也不支持浏览器标签页级静音。

本轮不包括：

- EQ、频谱、音效、200% 增强、Audio Unit 或任何持续 DSP。
- 应用路由、输出设备切换、收藏、配置场景、全局快捷键或定时静音。
- 虚拟驱动、自动更新框架、网络服务或新第三方依赖。
- 改变现有系统音频捕获权限模型。
- 修复旧版设置 schema 迁移或重做退出清理；它们是独立问题，需各自设计和真实设备验证。
- 自动发布 GitHub Release。代码、文档和产物验证完成后再单独决定是否公开发布。

## 设计

### 1. 单一会话音量来源

会话身份由 `(pid, bundleIdentifier)` 共同确定；`applicationVolumes[pid]` 是该身份仍在活跃列表期间的当前会话值。对于 Process Tap 应用：

1. 会话身份第一次进入列表时，以 `settingsStore.resolvedGain(bundleID)` 初始化；它会返回记住的值或用户配置的默认输出增益。
2. 后续发现相同 PID 且 bundle ID 相同时保留 `applicationVolumes[pid]`，不再用设置值覆盖。
3. 如果相同 PID 在现有 0.8 秒宽限期内对应了不同 bundle ID，必须在初始化新应用前停止旧 Tap、取消旧异步任务，并清理旧音量、确认值、编辑状态、静音恢复值和手动接管状态。
4. 会话身份离开列表并超过宽限期后执行同一清理；下次出现重新初始化。
5. 所有值进入状态前都限制在 0...1。

AppleScript 可控应用继续以实际异步读取结果更新界面；读取失败时继续保留最后一次已确认值。会话优先规则只修复没有公开内部音量可读的 Process Tap 路径，不伪造第三方应用内部滑杆值。

把“会话身份相同且已有会话值时优先，否则使用初始值并夹紧”的规则放进 `AppVolumeControlCore/VolumePolicy.swift`。ViewModel 维护 PID 到 bundle ID 的轻量映射，并通过一个统一清理函数处理退出和 PID 复用，使规则不依赖 AppKit、CoreAudio 或真实音频设备即可测试。

### 2. 统一有效接管谓词

有效接管条件定义为：

```text
explicitlyArmed || automaticallyAttachNewApps
```

该规则放进可测试的 core 层。必须区分三个状态：

- `attachmentAllowed`：用户允许尝试接管，即手动启用或自动接管设置开启；
- `canEdit`：系统版本支持、存在输出对象且管理器当前没有失败，允许用户发起增益变化；
- `isActive`：Tap 已实际连接，只能用于显示“已连接”，不能由 `attachmentAllowed` 推断。

界面可写条件是 `attachmentAllowed && canEdit`。这样 100% 时尚未创建 Tap 的应用仍可把滑杆往下调并触发按需创建，而权限拒绝或创建失败后不会继续显示一个假装生效的静音按钮。以下位置共同使用这些统一状态：

- `ProcessGainManager.reconcile` 的 `attachmentAllowed`；
- `sliderEnabled(for:)`；
- `tapStatusText(for:)`；
- 行内“启用独立增益”按钮是否出现；
- `independentGainEnabled(for:)`，重命名或改为表达“允许接管”的语义。

自动接管关闭时，点击静音不会隐式把未启用的应用加入手动集合。自动接管开启但 Tap 尚未连接时，界面显示真实的等待或失败状态，不把“允许接管”写成“已连接”。

### 3. 会话级静音状态机

ViewModel 增加 `muteRestoreVolumes: [pid_t: Double]`，只存于内存，不写 `UserDefaults`。`VolumePolicy` 定义唯一的 `muteThreshold = 0.000_1`；数值小于或等于该阈值时视为静音，按钮、状态转换和测试全部复用它。

回退值由 ViewModel 显式传入纯状态机。Process Tap 应用依次选择第一个大于静音阈值的候选：`settingsStore.resolvedGain(bundleID)`、用户配置的 `defaultOutputGain`、全新安装基准 75%；AppleScript 应用使用 75% 基准。这样既尊重自定义默认值，也避免已记住值和默认值同时为 0 时“恢复”仍是 0。候选解析放在 `VolumePolicy` 中并单独测试，静音状态机不读取产品设置。

| 当前值 | 恢复值 | 操作结果 | 新恢复值 | 是否写记忆设置 |
| --- | --- | --- | --- | --- |
| 大于阈值 | 任意 | 设为 0 | 保存当前值 | 否 |
| 小于或等于阈值 | 有效且大于阈值 | 恢复该值 | 清除 | 否 |
| 小于或等于阈值 | 无 | 恢复传入的回退值 | 清除 | 否 |

附加规则：

- 用户用滑杆把静音应用调到非零值，视为手动恢复并清除旧恢复值。
- 用户直接把滑杆拖到 0%，不会自动猜测一个恢复值；此时点击恢复使用上述回退值。这个 0% 同样是会话静音，不得覆盖已记住的非零增益。
- 会话身份离开活跃列表、PID 对应的 bundle ID 改变或应用被替换时清理恢复值，避免 PID 复用造成串音量状态。
- 静音和恢复都复用现有写入路径：AppleScript 应用调用已有异步写入，Process Tap 应用调用已有实时增益更新。
- 音量写入携带明确意图：只有大于静音阈值的正常滑杆提交可调用 `settingsStore.storeGain`。按钮静音、按钮恢复以及滑杆提交到静音阈值以内都不可持久化，避免下次会话从 0% 开始。
- 任何写入失败都沿用现有回退：AppleScript 保留最后确认值；Process Tap 由管理器报告失败并保持 fail-open，不新增无限重试。

状态转换本身放进 core 层的纯函数，并返回目标值、原恢复值和建议的新恢复值。ViewModel 只负责应用结果和调用相应音频后端。

AppleScript 写入是异步的，因此 `writeNativeVolume` 增加只对当前任务身份生效的完成结果：

- 请求静音时可乐观显示 0，并暂存建议恢复值；写入成功后保留，失败后恢复原恢复值与最后确认音量。
- 请求恢复时可乐观显示目标值；写入成功后清除恢复值，失败后恢复原恢复值与最后确认音量，允许重试。
- 新的滑杆或静音操作继续取消旧延迟写入；旧任务的终止回调因身份不匹配，不得覆盖新状态。

AppleScript 路径改变的是受支持应用自己的原生音量。其恢复记录只存在于 AppVolumeControl 内存中；如果目标应用或 AppVolumeControl 在恢复前退出，第三方应用可能保留 0%。README 必须诚实写明这一点。Process Tap 路径只改变本项目的会话级输出增益，不改变应用内部值。

### 4. 界面

每个当前可调节的应用在滑杆旁增加一个无文字的系统符号按钮：

- 非零：`speaker.wave.2.fill`，点击后静音；
- 小于或等于静音阈值：`speaker.slash.fill`，点击后恢复。

按钮提供中文可见帮助与完整可访问性标签，例如“静音 抖音”和“恢复 抖音 音量”。符号不依赖颜色表达状态。未允许接管的 Process Tap 行继续显示现有“启用独立增益”入口，不出现一个会偷偷申请权限的静音按钮。

为了保持当前窄面板，静音按钮使用约 20 点点击视觉宽度并与滑杆同排；若实际 UI 验证出现文本截断，只微调滑杆宽度或面板宽度，不新增第二行。

### 5. 数据与生命周期

- 不修改 `VolumeSettings` schema，不新增持久化键。
- `applicationVolumes`、`confirmedApplicationVolumes`、编辑状态、静音恢复值、异步读写任务和手动接管状态都随当前会话身份一起清理。
- 持久化仍按 bundle ID 工作；会话字典以 PID 索引但必须同时核对 bundle ID，既避免同 bundle 的两个进程互相覆盖，也避免 PID 复用继承旧状态。
- 不增加 Timer、后台线程或音频回调中的锁；静音只是把现有原子增益目标设为 0 或恢复值。
- 不修改现有显式接管默认值：`automaticallyAttachNewApps` 仍默认为 `false`。

## 测试设计

先增加会失败的纯逻辑测试：

1. 当前会话值存在时优先于设置初始值。
2. 当前会话值不存在时使用初始值，且输入被夹紧到 0...1。
3. 相同 PID、不同 bundle ID 即使仍在宽限期内，也不得继承旧 42%、恢复值或手动接管状态。
4. 从 42% 静音得到 0%，并记录 42%。
5. 从 0% 且有 42% 恢复值得到 42%，随后清除恢复值。
6. 从 0% 且没有恢复值、自定义回退为 50% 时得到 50%；已记住值和自定义默认都为 0 时使用 75%，不能恢复到 0。
7. `muteThreshold` 边界两侧的静音判断一致。
8. AppleScript 异步写成功时提交建议恢复值，失败时保留原恢复值；过期任务结果不改变新状态。
9. 大于静音阈值的正常滑杆提交允许持久化；按钮静音、按钮恢复和直接把滑杆拖到 0% 都禁止持久化。已有 42% 记忆时拖到 0%，持久化值仍为 42%，下次会话不从 0% 初始化。
10. 手动启用、自动接管、两者都关闭三种情况下，有效接管谓词分别正确，并区分 allowed-but-inactive 与 active。

## 端到端验证

- 冷启动、打开/关闭面板、无活跃音频应用、只有 AppleScript 应用、只有 Process Tap 应用四种界面状态。
- Process Tap 行调到 42%，等待至少三个现有刷新周期，确认仍为 42%。
- 手动启用路径与自动接管路径分别检查滑杆、状态文字、按钮和管理器状态一致。
- 42% → 静音 → 恢复，确认回到 42%；再确认记忆设置中的值未被 0% 覆盖。
- 通过生产代码实际复用的纯写入计划验证：正常提交允许调用 `storeGain`，静音与恢复禁止调用。若验证时存在可安全控制的 Process Tap 应用，再用隔离 `UserDefaults` suite 做黑盒复核；不得污染用户的正式设置域，也不得为了测试主动播放用户媒体。
- 应用离开活跃列表后确认会话和恢复值被清理；用纯逻辑测试覆盖同 PID、不同 bundle ID 的复用情形。
- 检查帮助文字和 README 都说明 Process Tap 是应用进程级输出增益，不是应用内部音量或浏览器标签页音量。
- 不主动播放用户媒体；若没有现成活跃音频，只对纯逻辑、空面板、构建和可见 UI 作已验证结论，把真实声音链路明确列为未验证。
- 对 `.app` 执行严格签名检查，检查架构和最低系统版本；重新生成 ZIP 与 SHA-256。
- 记录变更前后 `.app`、可执行文件和 ZIP 的字节数。若 `.app` 增量超过 50 KiB，必须解释原因或回退多余实现。
- 面板关闭和打开各采样一次空闲 CPU/RSS；没有可比负载时不宣称性能提升。

## 风险与回退

- **音量仍被刷新覆盖**：纯函数测试之外，必须做三个刷新周期的可见状态验证；失败则不交付。
- **自动接管显示错误**：所有 UI 分支只能调用统一谓词，不再直接各自判断 `armedProcessIDs`。
- **静音覆盖记忆值**：静音写入路径显式携带“不持久化”意图，并通过生产代码复用的纯写入计划测试锁定；有安全测试对象时再做隔离设置黑盒复核。
- **PID 复用**：每次发现同时核对 PID 与 bundle ID；身份变化先停止旧 Tap、取消旧任务并清理全部会话状态。
- **异步完成乱序**：AppleScript 完成结果必须匹配当前任务身份；失败回滚原恢复值，过期结果不修改新操作。
- **权限或 Tap 创建失败**：不自动扩权，不循环重试，沿用 fail-open 并显示真实状态。
- **界面拥挤**：只允许调整现有控件宽度，不扩展成复杂混音器。
